## Executive Summary

This PR vendors `src/go/guestagent` and `src/go/networking` (filter-repo'd from `rancher-desktop@c8cd431`, ~494 commits) into the repo and rewires the Dockerfile to build the four VM binaries from local sources instead of cloning upstream. The mechanical change — `git clone … rancher-desktop` removed; `COPY src /rd` plus per-module `WORKDIR + go build` blocks — is correct and removes the only network egress from Stage 1 of the image build. The cost is structural: this repo now owns the imported source, but the supporting machinery (CI test invocation, repo overview, dead Windows-host tree) does not yet reflect that ownership.

The reviews surface two categories of findings. **PR-specific structural issues** (I1–I3): the project's own steering text contradicts the new layout, the ~1250 lines of imported tests have no signal in this repo, and the Windows host-side `cmd/host/` tree plus its winio/hvsock dependencies are vendored but never built. **Inherited bugs in the imported code** (I4–I12): a `RemoveAll` path that drops UDP protocol info, an inverted `isTimeout` predicate, a `go vet` failure that breaks `go test ./...` on Linux, port-keyed maps that clobber multi-IP bindings, an iptables-rule map that leaks for multi-port containers, a `vm-switch` retry loop that reuses a closed file descriptor, and several other concurrency/lifecycle gaps. None of these are introduced by the PR — they exist in upstream `rancher-desktop` at the import SHA — but they are this repo's problem the moment the import lands.

No critical, fresh-introduced regressions. Verdict is *merge with fixes*: ship the structural ones with the PR, file the inherited bugs as follow-up issues here (and ideally upstream).

### Inherited from upstream (this repo now ships them)

I4. **`isTimeout` returns false for every timeout error** — `src/go/guestagent/pkg/kube/watcher_linux.go:208-220` [Codex GPT 5.5]

```go
func isTimeout(err error) bool {
	type timeout interface {
		Timeout() bool
	}

	var timeoutError timeout

	if !errors.As(err, &timeoutError) {
		return timeoutError != nil && timeoutError.Timeout()
	}

	return false
}
```

The condition is inverted. When `errors.As` *fails*, `timeoutError` is nil, so the inner expression is always false. When `errors.As` *succeeds*, the function falls through to `return false`. The two callers — `watcher_linux.go:119` (sleep-and-retry on watcher establishment) and `servicewatcher_linux.go:81-82` (treat watcher timeout as benign) — both depend on this returning true for actual timeouts. As written, transient Kubernetes API timeouts surface as fatal errors instead of being retried.

Fix:

```diff
-	if !errors.As(err, &timeoutError) {
-		return timeoutError != nil && timeoutError.Timeout()
+	if errors.As(err, &timeoutError) {
+		return timeoutError.Timeout()
 	}

 	return false
```

I7. **Listener and UDP-conn maps key on port only, clobbering same-port-different-IP bindings** — `src/go/networking/pkg/portproxy/server.go:45-49,127,161,212,229` [Codex GPT 5.5, Gemini 3.1 Pro]

```go
// map of UDP port number as a key to associated UDPConn
```

Both maps key on `int` port. When Docker reports two bindings for the same port on different host IPs (e.g., `127.0.0.1:8080` and `192.168.x.y:8080`), the second add overwrites the first map entry. I9. **`Iptables.ForwardPorts` advances state before `Add` succeeds** — `src/go/guestagent/pkg/iptables/iptables.go:88-90,123-126` [Gemini 3.1 Pro]

```go
added, removed := comparePorts(ports, newPorts)
ports = newPorts
…

	log.Errorf("iptables scanner failed to forward portmap for %s: %s", name, err)

```

`ports` advances to `newPorts` before the per-port `apiTracker.Add` calls run. A failure on `Add` only logs and continues. On the next tick `comparePorts` sees the failed port as already known, so `added` is empty and the forward never retries. I10. **vm-switch retries with a closed file descriptor** — `src/go/networking/cmd/vm/switch_linux.go:84,97-112,127-131` [Gemini 3.1 Pro]

```go
connFile := os.NewFile(uintptr(vsockFD), "vsock connection")
…
for {
	…
	default:
		if err := run(ctx, cancel, connFile); err != nil {
			logrus.Error(err)
		}
		// Wait one second before attempting to re-establish connection.
		time.Sleep(time.Second)
	}
}
```

`connFile` comes from the parent process via vsock-fd argument and `os.NewFile`. `run` defers `connFile.Close()` (line 128). On the second iteration the loop calls `run` again with the now-closed `*os.File`; every read/write fails immediately, the loop sleeps a second, and the process spins forever, never re-establishing the connection. There is no path in `vm-switch` to recreate the parent-supplied vsock — only the parent (`network-setup`) can do that.

```diff
-				logrus.Error(err)
-			}
-			// Wait one second before attempting to re-establish connection.
-			time.Sleep(time.Second)
+		default:
+			err := run(ctx, cancel, connFile)
+			logrus.Errorf("run exited: %v; terminating so the parent restarts us", err)
+			os.Exit(1)
		}
```

I11. **WSL UDP proxy never reads VM responses** — `src/go/networking/pkg/portproxy/server.go:169-201` [Gemini 3.1 Pro]

```go
func (p *PortProxy) acceptUDPConn(sourceConn *net.UDPConn, targetAddr *net.UDPAddr) {
	targetConn, err := net.DialUDP("udp", nil, targetAddr)
	…
	for {
		n, addr, err := sourceConn.ReadFromUDP(b)
		…
		n, err = targetConn.Write(b[:n])
		…
	}
}
```

The loop reads from the host-side `sourceConn` and writes to the upstream `targetConn`, but never reads from `targetConn` to write back to the client. Any UDP response the upstream sends — DNS replies, NTP, mDNS — disappears. The WSL trust model in `deep-review-context.md` does not lower the bar here; this is a forwarding contract issue, not a host-share concern.

Fix: launch a paired goroutine that reads from `targetConn` and writes back via `sourceConn.WriteToUDP(buf, addr)`. Multi-client UDP needs a per-client target connection map; for a single-client port-forward, the simpler pair is enough.

I12. **`servicewatcher_linux` calls `WaitForCacheSync` before `Start`** — `src/go/guestagent/pkg/kube/servicewatcher_linux.go:105-106` [Gemini 3.1 Pro]

I13. **TCP proxy half-close drops in-flight upstream data** — `src/go/networking/pkg/utils/pipe.go:35-49` [Gemini 3.1 Pro]

```go
go func() {
	if _, err := io.Copy(upstream, conn); err != nil { … }
	if err = upstream.Close(); err != nil { … }
}()

if _, err := io.Copy(conn, upstream); err != nil { … }
if err = upstream.Close(); err != nil { … }
```

When the client EOFs, the goroutine's `upstream.Close()` tears down the whole TCP connection, including the upstream→client direction. Any data the upstream still has in flight goes out as RST. Long-lived request-response protocols (HTTP keep-alive, SSH, TLS half-closes during shutdown) drop their tail.

Fix: half-close instead of full-close on the client→upstream direction.

```go
if cw, ok := upstream.(interface{ CloseWrite() error }); ok {
	cw.CloseWrite()
} else {
	upstream.Close()
}
```

I14. **Static K8s API mapping sent once with no retry** — `src/go/guestagent/main.go:140-160`, `src/go/guestagent/pkg/forwarder/wslproxy.go` [Gemini 3.1 Pro]

```go
if err := wslProxyForwarder.Send(k8sAPIPortMapping); err != nil {
	return fmt.Errorf("failed to send a static portMapping event to wsl-proxy: %w", err)
}
```

The static port mapping for the K8s API is sent exactly once at guestagent startup. If `wsl-proxy` is not yet listening on `/run/wsl-proxy.sock`, guestagent dies with the error. If `wsl-proxy` is up at startup but later restarts, guestagent has no reconciliation path — `wsl-proxy` comes back without the K8s mapping and the API stays unreachable from the host.

Fix: retry the initial send with a bounded backoff (e.g., 30s × 1s) instead of failing on first refusal, and re-send any static mappings whenever the WSL-proxy socket reconnects. A periodic sync from `APITracker.portStorage` to `wsl-proxy` would make all static-and-dynamic mappings survive proxy restarts.


I15. **`Close()` blocks indefinitely on active forwards** — `src/go/networking/pkg/portproxy/server.go:259-279` [Gemini 3.1 Pro]

```go
func (p *PortProxy) Close() error {
	p.cleanupListeners()
	p.cleanupUDPConns()
	err := p.listener.Close()
	…
	close(p.quit)
	p.wg.Wait()
	return nil
}
```

`cleanupListeners` and `cleanupUDPConns` close the listening sockets but not the data connections that `acceptTraffic` and `acceptUDPConn` already accepted (each one increments `wg`). `utils.Pipe` blocks on `io.Copy` until both sides EOF, and `acceptUDPConn` blocks on `ReadFromUDP` until `sourceConn` closes — so as long as a single keepalive or streaming session is open, `wg.Wait()` never returns. The wsl-proxy shutdown path hangs until systemd's `TimeoutStopSec` force-kills it.

Fix: track the active `net.Conn`s in a slice or map, and close them in `Close()` before waiting on `wg`. The clean shutdown is "stop accepting → close in-flight → wait for goroutines."

## Design Observations

### Concerns

**Vendoring vs. upstream module dependency (in-scope)** [Claude Opus 4.7]. The PR description notes the source SHA and the `replace` directive, but does not articulate the operational benefit of vendoring over a pinned `go get` against tagged upstream releases. The alternative — keep `go.mod` pointing at a tagged `rancher-desktop` release, vendor a tarball into the build cache for offline use — would let dependabot keep this repo's modules current, run upstream's tests, and drop S1–S5 from this review. Jandubois's PR comment ("Even that seems excessive if we move the sources eventually to `rancher-desktop-daemon`") flags the same tension. Worth one paragraph in the merge commit or PR description on why we vendor here-and-now rather than waiting for the daemon repo.

**Inherited bugs come with ownership (in-scope)** [Claude Opus 4.7]. Ten of the fifteen Important findings (I4–I15) are pre-existing upstream bugs surfaced by the import. Before this PR they belonged to `rancher-desktop`; after, they belong here too. The team needs an explicit triage policy: file each as a follow-up issue against this repo, sync with upstream so fixes go in once, and set a cadence for re-importing the upstream sources or backporting fixes here.

**No reconciliation between `guestagent` and `wsl-proxy` (future)** [Gemini 3.1 Pro]. The `APITracker` fires events at `wsl-proxy` and forgets them. A `wsl-proxy` restart wipes its mapping table and there is no resync — the closest thing to a recovery path is a container restart that re-emits the event. A pull-based contract (`wsl-proxy` queries `guestagent` on startup) or a periodic full-state push would survive proxy restarts. I14 is the visible symptom; the structural fix is broader.

### Strengths

### [Gemini 3.1 Pro]

### Executive Summary

This PR successfully migrates the `guestagent` and `networking` Go sources into the local repository, streamlining the build process by eliminating external clones. While the integration into the repo is structurally sound, a deep review of the migrated code reveals several critical flaws inherited or introduced along the way. These include a unidirectional UDP proxy that drops all VM responses, a file-descriptor lifecycle bug in `vm-switch` that traps it in an infinite failure loop upon disconnection, and an iptables rule leak in the Docker event monitor for multi-port containers. Several important issues related to proxy shutdown hangs, static port mapping loss, and Informer cache synchronization were also identified.

### Findings

#### Critical Issues

**C1. One-way UDP packet forwarding ignores replies** — `src/go/networking/pkg/portproxy/server.go:169-201`
```go
func (p *PortProxy) acceptUDPConn(sourceConn *net.UDPConn, targetAddr *net.UDPAddr) {
	// ...
	for {
		b := make([]byte, p.config.UDPBufferSize)
		n, addr, err := sourceConn.ReadFromUDP(b)
		// ...
		n, err = targetConn.Write(b[:n])
		// ...
	}
}
```
The UDP proxy reads from the host (`sourceConn`) and forwards to the VM (`targetConn`), but there is no corresponding read from `targetConn` to write back to `sourceConn`. As a result, any UDP response returned by the VM is permanently dropped. This completely breaks request-response UDP protocols like DNS.
*Fix:* At a minimum, launch a goroutine to read from `targetConn` and use `sourceConn.WriteToUDP` to send the response back to `addr`. Note that for full multi-client support, the proxy should map active target connections per client address. (critical, regression)

**C2. `vm-switch` retry loop infinitely loops on closed connection** — `src/go/networking/cmd/vm/switch_linux.go:88-91`
```go
			if err := run(ctx, cancel, connFile); err != nil {
				logrus.Error(err)
			}
			// Wait one second before attempting to re-establish connection.
			time.Sleep(time.Second)
```
The `connFile` (vsock file descriptor) is passed into `run()`, which defers `connFile.Close()`. When an error occurs and `run()` returns, the `connFile` is closed. However, the `main` loop sleeps for 1 second and then calls `run(..., connFile)` again with the *same* closed file. The next `run()` immediately fails on read/write, returning an error, and spins forever. `vm-switch` has no mechanism to recreate the parent-provided vsock connection.
*Fix:* Terminate the `vm-switch` process on failure. This enables systemd to restart the parent `network-setup.service` and re-establish the namespace and vsock connection correctly.
```diff
-			if err := run(ctx, cancel, connFile); err != nil {
-				logrus.Error(err)
-			}
-			// Wait one second before attempting to re-establish connection.
-			time.Sleep(time.Second)
+			err := run(ctx, cancel, connFile)
+			logrus.Errorf("run exited with: %v, terminating process", err)
+			os.Exit(1)
```
(critical, gap)

**C3. `iptablesRulesToDelete` map leaks rules for multi-port/multi-network containers** — `src/go/guestagent/pkg/docker/events.go:275-279`
```go
			e.iptablesRulesToDelete[containerID] = iptablesDeleteLoopbackRuleCmd(
				ctx,
				portProto.Proto(),
				portBinding.HostPort,
				fmt.Sprintf("%s:%s", containerIP, portProto.Port()))
```
The map is keyed only by `containerID`. When a container is attached to multiple networks or exposes multiple ports, the inner loops overwrite the map entry. Only the *last* iptables deletion command is saved. When the container stops, only the last rule is deleted, permanently leaking all other iptables rules for that container in the `DOCKER` chain.
*Fix:* Store an array of deletion commands per container.
```diff
-	iptablesRulesToDelete map[string]*exec.Cmd
+	iptablesRulesToDelete map[string][]*exec.Cmd
```
(critical, gap)

#### Important Issues

**I1. `activeListeners` and `activeUDPConns` clobber listeners on the same port with different IPs** — `src/go/networking/pkg/portproxy/server.go:37-41`
```go
	// map of TCP port number as a key to associated listener
	activeListeners map[int]net.Listener
```
The proxy maps listeners by the `int` port. If two containers bind to the same port on different host IPs (e.g., `127.0.0.1:8080` and `192.168.1.5:8080`), the second connection silently overwrites the first in the map. When the second container is removed, it deletes the map entry. The listener for the first container is leaked forever and cannot be stopped.
*Fix:* Key the maps with a string that includes the IP (e.g., `IP:Port`). (important, regression)

**I2. `Iptables.ForwardPorts` loop consumes new ports on API tracker failure** — `src/go/guestagent/pkg/iptables/iptables.go:88`
```go
		added, removed := comparePorts(ports, newPorts)
		ports = newPorts
```
The polling loop identifies newly added ports and immediately updates its known state (`ports = newPorts`). If the subsequent call to `i.apiTracker.Add(...)` fails, the error is logged and the loop continues. In the next iteration, the port is no longer considered "new", and the `Add` operation is never retried, permanently breaking the port mapping.
*Fix:* Do not update `ports` for mappings that failed to apply; only commit the state delta upon success. (important, gap)

**I3. `Close()` hangs indefinitely on active data connections** — `src/go/networking/pkg/portproxy/server.go:271`
```go
func (p *PortProxy) Close() error {
    // ...
	p.wg.Wait()
```
`Close()` calls `p.cleanupListeners()` (which unblocks `Accept()`) and then blocks on `p.wg.Wait()`. However, `Close()` does not terminate the underlying active `net.Conn` data transfers in `utils.Pipe` or `acceptUDPConn`. Thus, `p.wg.Wait()` will block forever if there are any keep-alive or streaming connections, causing the `wsl-proxy` shutdown sequence to hang until systemd force-kills it.
*Fix:* Track the active `net.Conn` data connections in a map/slice and aggressively close them during `Close()`. (important, regression)

**I4. Disconnected `wsl-proxy` crashes `guestagent` and static mapping is permanently lost** — `src/go/guestagent/main.go:138-140`
```go
		if err := wslProxyForwarder.Send(k8sAPIPortMapping); err != nil {
			return fmt.Errorf("failed to send a static portMapping event to wsl-proxy: %w", err)
		}
```
The static K8s API port mapping is sent exactly once during startup without a retry loop. If `wsl-proxy` is not yet running, `guestagent` crashes immediately. Even if startup succeeds, if `wsl-proxy` crashes and restarts later, `guestagent` has no mechanism to re-send this static mapping, resulting in a silent, permanent loss of the K8s API proxy.
*Fix:* Add a retry loop for `wsl-proxy` availability at startup, and consider reconciling static mappings periodically to survive proxy restarts. (important, gap)

**I5. Informer started *after* `WaitForCacheSync` rendering the wait a no-op** — `src/go/guestagent/pkg/kube/servicewatcher_linux.go:105-106`
```go
	informerFactory.WaitForCacheSync(ctx.Done())
	informerFactory.Start(ctx.Done())
```
Because `WaitForCacheSync` checks the status of *started* informers, calling it before `Start()` makes it return immediately. The cache is not yet synced when the subsequent manual `List()` is executed. As a result, `handleUpdate` is invoked for every existing service manually, and shortly after, the Informer completes its own cache sync and fires `AddFunc` for the exact same services, duplicating every initial event.
*Fix:* Reverse the order of `Start` and `WaitForCacheSync`. Remove the manual `List()` entirely, as the Informer's `AddFunc` inherently processes all initial objects upon sync. (important, gap)

**I6. TCP proxy breaks half-closed connections** — `src/go/networking/pkg/utils/pipe.go:34-36`
```go
		if _, err := io.Copy(upstream, conn); err != nil { ... }
		if err = upstream.Close(); err != nil { ... }
```
When the client (`conn`) finishes writing and sends an EOF, `io.Copy(upstream, conn)` unblocks and the proxy calls `upstream.Close()`. This abruptly tears down the entire TCP connection. If the VM (`upstream`) was still transmitting data back to the client, that data is dropped and an RST is sent.
*Fix:* Use `CloseWrite()` to gracefully half-close the upstream connection.
```go
		if cw, ok := upstream.(interface{ CloseWrite() error }); ok {
			cw.CloseWrite()
		} else {
			upstream.Close()
		}
```
(important, gap)
