## Executive Summary

PR #37 introduces `rdd-guest`, a small Go daemon that runs in the WSL2 utility VM, listens on Hyper-V vsock port 6660, and proxies bytes to `/var/run/docker.sock`. The Dockerfile builds it from `src/rdd-guest`, the kiwi build copies it into `/usr/local/bin`, and `config.sh` enables a systemd unit gated by `ConditionVirtualization=wsl` so only WSL profiles activate the bridge.

The core proxy logic is sound — half-close propagation via `CloseWrite()` matches the Docker API's hijacked-stream contract, and the `signal.NotifyContext` shutdown path closes the listener cleanly. Three issues warrant fixes before merge: the listener accepts connections from any vsock CID (Critical, security), a 3.5 MB statically-linked x86-64 ELF binary slipped in alongside the source (Important, hygiene), and the `halfCloser` type assertions are unguarded (Important, robustness). Five smaller suggestions cover documentation drift, module hygiene, and a graceful-shutdown gap.

Structure: 1 critical, 2 important, 5 suggestions, plus design observations on the upstream-import TODO and unit ordering.

## Critical Issues

C1. **Vsock listener accepts connections from any CID** — `src/rdd-guest/main.go:29` [Gemini 3.1 Pro]

```go
l, err := vsock.Listen(vsockPort, nil)
```

`vsock.Listen` with a nil config binds to `VMADDR_CID_ANY`, so the listener accepts connections from CID 2 (the Windows host, the intended caller) **and** from any process inside the same lightweight utility VM. WSL2 runs all distros — the rancher-desktop distro plus user distros such as Ubuntu — in a shared LxVM with a single kernel and a single vsock namespace. An unprivileged process in any of those distros can dial `vsock.Local` (CID 1) on port 6660 and reach this listener; `rdd-guest` runs as root and unconditionally proxies to `/var/run/docker.sock`, granting that process root-equivalent Docker API access and bypassing the socket's `root:docker 0660` permissions.

The bridge's only legitimate caller is the Windows-side daemon over Hyper-V vsock (peer CID = `VMADDR_CID_HOST`). Filter on the peer CID at accept time:

```diff
 		conn, err := l.Accept()
 		if err != nil {
 			if ctx.Err() != nil {
 				return
 			}
 			log.Printf("rdd-guest: accept: %v", err)
 			continue
 		}
+		addr, ok := conn.RemoteAddr().(*vsock.Addr)
+		if !ok || addr.ContextID != vsock.Host {
+			log.Printf("rdd-guest: rejected connection from %v", conn.RemoteAddr())
+			conn.Close()
+			continue
+		}
 		go handleConn(conn)
```

Severity rests on Rancher Desktop's threat model. If multi-distro isolation is *not* a security boundary in this product (the user already has root in their own distro and Rancher Desktop intentionally shares Docker with sibling distros via other channels), the finding drops to defense-in-depth. Worth confirming with the daemon-side design before merging — but the check is one line and fails closed, so the safer default is to land it.

## Important Issues

I1. **Pre-built ELF binary committed to the source tree** — `src/rdd-guest/rdd-guest` [Claude Opus 4.7, Codex GPT 5.5, Gemini 3.1 Pro]

```
src/rdd-guest/rdd-guest  ELF 64-bit LSB executable, x86-64,
                         statically linked, 3,682,189 bytes
```

A 3.5 MB statically-linked Linux x86-64 ELF binary was committed alongside the source. The Dockerfile builds the same binary from source in the `gobuild` stage at `Dockerfile:20-22` (`go build -ldflags '-s -w' -o /go/bin/rdd-guest .`) and copies the freshly-built artifact into the kiwi description at `Dockerfile:37`; the checked-in copy is never consumed. The sibling `src/rd-init/` directory contains no equivalent binary, so this is unintentional. Three downsides: the binary permanently bloats the repo (git cannot re-deduplicate binary blobs the way it does text), it ships in every clone and release tarball, and it risks shipping a stale or differently-built artifact than the Dockerfile produces if anyone reaches for it directly. The committed binary is also x86-64 only, so an aarch64 user who runs it locally would get an exec error.

Fix: remove the binary and add an ignore rule covering both per-module binaries.

I2. **Unchecked type assertions to `halfCloser` will panic on upstream type changes** — `src/rdd-guest/main.go:75` [Claude Opus 4.7, Gemini 3.1 Pro]

```go
pipe(vsockConn.(halfCloser), dockerConn.(halfCloser))
```

Both assertions are unguarded. Today they succeed: `*vsock.Conn` from `mdlayher/vsock` v1.2.1 and `*net.UnixConn` from `net.Dialer.DialContext("unix", …)` both expose `CloseWrite() error`. But the static contracts do not require it — `net.Listener.Accept()` returns `net.Conn` and `net.Dialer.DialContext` returns `net.Conn`, neither of which guarantees `CloseWrite`. A future minor-version bump in `mdlayher/vsock` that wraps the conn (e.g., a context-cancellable adapter) crashes the agent on the first incoming connection. Systemd's `Restart=on-failure` then flaps the service, and every retry hits the same panic.

Fix: use the comma-ok idiom and drop the connection on mismatch.

```diff
-	pipe(vsockConn.(halfCloser), dockerConn.(halfCloser))
+	vsockHC, ok := vsockConn.(halfCloser)
+	if !ok {
+		log.Printf("rdd-guest: vsock conn does not support CloseWrite")
+		return
+	}
+	dockerHC, ok := dockerConn.(halfCloser)
+	if !ok {
+		log.Printf("rdd-guest: docker conn does not support CloseWrite")
+		return
+	}
+	pipe(vsockHC, dockerHC)
```

S5. **Active connections are severed at shutdown** — `src/rdd-guest/main.go:37-40` [Gemini 3.1 Pro]

```go
go func() {
	<-ctx.Done()
	l.Close()
}()
```

On SIGTERM, `l.Close()` unblocks `Accept` and `main` returns. Active proxy connections — long-running `docker logs -f`, `docker events`, hijacked `docker exec -it` streams — are abruptly severed when the program exits. Track in-flight `handleConn` goroutines with a `sync.WaitGroup` and wait for them (with a deadline) before returning, so the bridge drains gracefully on systemd reload/restart.

## Design Observations

### Concerns

- **(future)** The inlined `halfCloser` / `pipe` / `handleConn` are explicitly temporary per the TODO at `src/rdd-guest/main.go:55-57` — they get replaced by `pkg/socketbridge` from `rancher-desktop-daemon` once that repo opens. Worth tracking as an issue so the cleanup actually happens; vendored "temporary" copies tend to ossify. [Claude Opus 4.7]
- **(in-scope)** The systemd unit has no `After=` ordering. Sibling units (`wsl-proxy.service`, `rancher-desktop-guest-agent.service`) lack ordering hints too, so this matches local convention. Failure mode is benign — an early connection logs a dial error and the Windows side retries — but `After=docker.socket` would let the first boot connection succeed cleanly when moby is selected. Skip if the Windows-side retry already absorbs this. [Claude Opus 4.7]
- **(in-scope)** Vsock port and Docker socket path are hardcoded in `main.go:20-23`. The port must stay in lockstep with the Windows-side daemon; either add a code comment pinning that contract, or accept flag overrides (`-port`, `-socket`) so an operator can manually bisect a wedged bridge. [Claude Opus 4.7]

### Strengths

- **(in-scope)** `pipe()` propagates EOF with `CloseWrite()` per direction rather than tearing both sides down on first EOF — the correct behavior for HTTP-over-Unix Docker traffic with hijacked streams (`docker exec -it`, `docker attach`). [Claude Opus 4.7, Gemini 3.1 Pro]
- **(in-scope)** Listener close-on-`ctx.Done()` plus `ctx.Err()` distinguishing shutdown from transient accept errors is clean signal handling for a tiny program. [Claude Opus 4.7]
- **(in-scope)** Defense in depth: `ConditionVirtualization=wsl` in the unit prevents the bridge from starting on macOS/Lima images even though the binary is copied into `/usr/local/bin` for all profiles. [Codex GPT 5.5, Gemini 3.1 Pro]
- **(in-scope)** `CGO_ENABLED=0` in the Dockerfile keeps the binary fully static and cross-arch friendly with no extra effort. [Claude Opus 4.7]
- **(in-scope)** Per-connection Docker dial (rather than a long-lived shared connection) means a Docker restart does not require restarting the bridge. [Codex GPT 5.5]

## Testing Assessment

No tests added. The repo has no Go test suite for `src/rd-init` either, so this is a continuation of existing convention rather than a regression. Codex ran `go test ./...` in `src/rdd-guest` (passes, no test files) and smoke-built for `linux/amd64` and `linux/arm64`. Verification today is by booting a WSL image. Scenarios that would matter most if a regression slipped in:

1. **Vsock peer-CID rejection (highest risk after C1):** dial from CID 1 (loopback inside the VM) and verify the connection is rejected before `rdd-guest` dials docker.sock.
2. **Half-close on hijacked streams:** `docker exec -it` from the host, exercising both `CloseWrite` paths in `pipe()`.
3. **Dial failure on missing socket:** with the containerd engine selected and `/var/run/docker.sock` absent, the bridge should log per-connection dial errors and not crash.
4. **Listener restart:** `systemctl restart rdd-guest` should rebind port 6660 cleanly with no stale-socket error.
5. **Concurrent connections:** many parallel host-side Docker calls.
6. **Graceful shutdown:** in-flight long-poll connection survives a `systemctl reload` (depends on S5).

## Review Process Notes

### Skill improvements

- **Add a review dimension on multi-tenant/shared-namespace exposure for new listeners.** When a PR introduces a network listener (vsock, Unix socket, TCP, named pipe), the review prompt should explicitly ask: who can reach this listener, and does the binding match the intended caller's address space? The current `dimensions.md` covers privilege escalation broadly, but the specific case "binds to ANY but only one caller is legitimate" is a recurring class — vsock CID-ANY, TCP `0.0.0.0` instead of `127.0.0.1`, abstract Unix sockets — and is easy to miss without the prompt naming it.
  *Why:* Two of three agents missed this on PR #37 even though the fix is one line. Naming the pattern in the prompt raises the chance future agents catch analogous issues across protocols.

### Repo context updates

- **Document Rancher Desktop's WSL2 trust model in `deep-review-context.md`.** Future reviews of WSL2-side components need to know whether multi-distro isolation is a security boundary in this product. If yes, agents should treat any new WSL2 listener as requiring peer-CID/peer-uid restriction. If no (e.g., Rancher Desktop intentionally shares Docker with sibling distros via other channels), agents can downgrade those concerns to defense-in-depth. Either answer changes severity calibration on this class of finding.
  *Why:* Severity on PR #37's C1 hinges entirely on this question, and neither the agents nor the orchestrator could resolve it from the diff alone.
- **Document the binary-output-in-source-tree pattern** if `src/<module>/<binary>` appearing in `git ls-files` is always a mistake in this repo (no module checks in its own build artifact). Worth codifying as a repo invariant so agents flag any future occurrence at Important without arguing about severity.
  *Why:* Three agents disagreed on severity for the binary commit on PR #37 (Critical / Important / Suggestion); a repo-context line settles it.

### [Gemini] — Pass 1

### Executive Summary

This PR introduces `rdd-guest`, a systemd-managed Go daemon for WSL2 that listens on a Hyper-V vsock port and bridges incoming connections to the local `/var/run/docker.sock`. The core proxying logic correctly handles TCP-like half-close semantics; however, the vsock listener lacks source authorization, allowing any unprivileged process within the shared WSL2 utility VM to bypass socket permissions and gain root-level Docker access. 

### Findings

#### Critical Issues

**C1. Missing authorization on vsock listener allows local privilege escalation** — `src/rdd-guest/main.go:39` (critical, regression)

```go
	for {
		conn, err := l.Accept()
		if err != nil {
// ...
		go handleConn(conn)
	}
```

By default, `vsock.Listen` binds to `VMADDR_CID_ANY`. In the WSL2 architecture, all WSL distributions (e.g., Ubuntu, Debian, and Rancher Desktop's backend distro) run within the same lightweight utility VM and share the same kernel and vsock namespace. Because `rdd-guest` runs as root and unconditionally proxies accepted connections to `/var/run/docker.sock`, any unprivileged user in any WSL distro can dial the loopback CID (`vsock.Local`, CID 1) or the VM's own CID on port 6660. This connects them to `rdd-guest` and grants unfettered root-level Docker API access, completely bypassing the UNIX socket's `root:docker 0660` file permissions.

Fix: Verify the incoming connection originates from the Windows host (`vsock.Host`, CID 2) before proxying it.

```diff
 		conn, err := l.Accept()
 		if err != nil {
 			if ctx.Err() != nil {
 				return
 			}
 			log.Printf("rdd-guest: accept: %v", err)
 			continue
 		}
 
+		addr, ok := conn.RemoteAddr().(*vsock.Addr)
+		if !ok || addr.ContextID != vsock.Host {
+			log.Printf("rdd-guest: rejected unauthorized connection from %v", conn.RemoteAddr())
+			conn.Close()
+			continue
+		}
+
 		go handleConn(conn)
```

**I1. Compiled binary committed to source control** — `src/rdd-guest/rdd-guest` (important, regression)

**I2. Unsafe type assertions risk daemon panic** — `src/rdd-guest/main.go:71` (important, regression)

```go
	pipe(vsockConn.(halfCloser), dockerConn.(halfCloser))
```

The connections are type-asserted to `halfCloser` without the `comma-ok` idiom. While `*vsock.Conn` and `*net.UnixConn` currently implement `CloseWrite() error`, an interface type assertion failure will panic and crash the entire `rdd-guest` daemon. This breaks Go defensive programming best practices, especially for network connections that could be mocked in tests or wrapped by future library updates.

Fix: Use the `comma-ok` idiom and gracefully drop the connection if it doesn't support half-closing.

```diff

 	if err != nil {
 		log.Printf("rdd-guest: dial docker: %v", err)
 		return
 	}
 	defer dockerConn.Close()
 
-	pipe(vsockConn.(halfCloser), dockerConn.(halfCloser))
+	vc, ok1 := vsockConn.(halfCloser)
+	dc, ok2 := dockerConn.(halfCloser)
+	if !ok1 || !ok2 {
+		log.Printf("rdd-guest: connection types do not support half-close")

+	}
+	pipe(vc, dc)
```

**S1. Abrupt connection termination on shutdown** — `src/rdd-guest/main.go:37-40`

```go
	go func() {
		<-ctx.Done()
		l.Close()
	}()
```

When the system receives a SIGTERM, `l.Close()` is called, causing `l.Accept()` to fail and `main` to exit immediately (line 42). Any active proxy connections (e.g., long-running `docker logs -f` or `docker events` from the Windows host) are abruptly severed. 

Fix: Use a `sync.WaitGroup` to track active `handleConn` goroutines and wait for them to finish (or add a short timeout context) before returning from `main`.
